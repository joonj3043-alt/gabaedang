# 상담 접수 연결 계약

현재 접수는 비활성입니다. 입력값은 브라우저 저장소에 저장하지 않으며 API가 연결되지 않으면 전송하지 않습니다.

## 연결 순서

1. 고객사 소유의 HTTPS API를 준비합니다. API 비밀키나 이메일 발송 인증키는 공개되는 config.js에 넣지 않습니다.
2. 서버가 JSON 요청을 검증하고 DB 또는 문의 관리 시스템에 접수 기록을 저장하도록 구현합니다.
3. 허용할 GitHub Pages/실제 도메인 Origin에 대한 CORS 및 OPTIONS 응답을 설정합니다. 서버에서 길이 제한, 필수 동의, 입력 검증, 요청 횟수 제한과 스팸 방어를 수행합니다. 클라이언트 검증만 신뢰하지 마세요.
4. 저장 성공 후 접수번호를 반환합니다. 단순 메일 발송 요청 시작을 접수 성공으로 처리하지 않도록 서버 계약을 정의하세요.
5. 개인정보처리방침을 검토하고 수탁자·보관 위치·보유 기간 등을 확정합니다.
6. `config.js` 설정을 채운 뒤 테스트 환경에서 성공·실패·타임아웃을 검수하고 운영 전환합니다.

## 요청

POST https://고객사-API/문의경로
Content-Type: application/json
Accept: application/json

```json
{"type":"라이더 지원","name":"테스트","phone":"테스트용 연락처","region":"선택 사항","message":"상담 내용","consent":true}
```

## 성공 응답

HTTP 201 또는 200, Content-Type: application/json

```json
{"ok":true,"receiptId":"실제 저장된 문의의 접수번호"}
```

## 실패

400/429/500 등의 오류 또는 ok:true·receiptId가 없는 응답은 성공 표시를 하지 않습니다. 15초 내 확인되지 않거나 네트워크가 끊기면 완료를 확인하지 못했다는 안내와 입력 내용을 유지합니다. 응답만 유실되었을 가능성이 있어 자동 재전송하지 않습니다. 운영 서버에서는 중복 접수 방지 키를 추가하는 것이 좋습니다.

일반 폼 서비스가 `{ok:true,receiptId}`와 다른 응답을 반환하면 서버 측 어댑터를 사용하거나 app.js의 성공 판정을 해당 서비스의 실제 계약에 맞게 수정하고 재검수해야 합니다. JSON POST를 지원하지 않는 서비스는 endpoint 입력만으로 연결되지 않습니다.

## 운영 전 실제 확인 목록

- 필수 항목 누락 및 동의 미선택 시 서버도 거부
- 정상 문의가 관리 시스템에 정확히 한 번 저장
- 수신 담당자 알림 및 접수번호 대조
- 4xx/5xx/비JSON/타임아웃 시 허위 성공 미표시
- CORS, 과다 요청 제한, 개인정보 삭제/보유기간 적용

이 항목들의 실제 서버 검수는 접수 서버 미제공으로 수행하지 않았습니다.
